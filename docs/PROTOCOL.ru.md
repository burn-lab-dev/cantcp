# Протокол cantcp

[English](PROTOCOL.md) | **Русский**

Разрабатывается **[BURN-LAB](https://burn-lab.ru)** — встраиваемый Linux:
драйверы, CAN и промышленная телеметрия.

## Кадры в потоке

`cantcp` переносит сырые кадры Linux SocketCAN в байтовом потоке TCP.
Пакет:

```
[magic 2 байта][type 1 байт][can_frame 16 | canfd_frame 72][CRC-8 1 байт]
```

- magic: по умолчанию `0xC3 0x3C`;
- type: `0x01` — `struct can_frame` (16 байт), `0x02` — `struct canfd_frame`
  (72 байта);
- кадр: побайтовый формат Linux SocketCAN (`can_id` little-endian, байт
  длины, выравнивание, данные);
- CRC-8 (по умолчанию полином `0x07`) по `magic + type + frame`.

Транспорт кадры не разбирает: `cantcpd` читает сырой кадр из сокета и
отправляет его одним пакетом, и наоборот. Разобранная модель (идентификатор,
флаги, данные) нужна `cantcp-cli` для отображения и ввода.

## Чего в протоколе нет

Протокол переносит только кадры:

- нет handshake, подписок и keepalive: соединение — просто TCP;
- нет аутентификации и шифрования: используйте TLS 1.3 (см. [TLS.ru.md](TLS.ru.md))
  или доверенный периметр;
- нет статистики: `cantcpd` отдаёт её по HTTP (см. [STATS.ru.md](STATS.ru.md));
- нет таймстампов: получатель ставит своё локальное время;
- нет управления потоком: при переполнении очереди клиента демон
  отбрасывает кадры и считает их.

Так транспорт остаётся минимальным, а библиотеки — маленькими. Всё, что
требует логики приложения (статистика, health-check, подписки), относится к
API сервера, а не к потоку кадров.

## Реализации

Протокол побайтово одинаково реализован парными библиотеками с общими
тестовыми векторами:

- Go: [cantcp-lib-go](https://github.com/burn-lab-dev/cantcp-lib-go) —
  `NewDecoder` / `NewEncoder` оборачивают `Split` / `Encode` в `io`-API;
- Python: [cantcp-lib-python](https://github.com/burn-lab-dev/cantcp-lib-python)
  — тот же API, `Parser` / `Decoder` / `Encoder`.

`cantcpd` и `cantcp-cli` используют библиотеку Go; Python-сервис или
утилита может общаться с демоном через библиотеку Python.

## Совместимость

- Версия протокола: **v0** (раскладка пакета выше). До v1.0.0 возможны
  ломающие изменения.
- Пределы кадров: CAN 2.0 (0..8 байт данных) и CAN FD (0..64 байта, длины
  из 4-битного поля DLC).
- Кадры ошибок переносятся как классические с флагом `CAN_ERR_FLAG` в
  идентификаторе; включаются в демоне через `can.error_frames`.
- Декодер, встретив мусор, синхронизируется на следующем magic: поток
  самосинхронизирующийся — сознательное свойство v0.

## Замечания по безопасности

CRC-8 — проверка разметки, не криптография: примерно одна из 256 случайных
последовательностей её проходит. Протокол не даёт целостности,
конфиденциальности и защиты от повторов. Для недоверенных сетей используйте
TLS 1.3, а незащищённый режим считайте инструментом стенда или сегмента.
См. [SECURITY.ru.md](../SECURITY.ru.md).
