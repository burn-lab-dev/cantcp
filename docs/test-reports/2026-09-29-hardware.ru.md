# Отчёт по физической шине — 2026-09-29

[English](2026-09-29-hardware.md) | **Русский**

Разрабатывается **[BURN-LAB](https://burn-lab.ru)** — встраиваемый Linux:
драйверы, CAN и промышленная телеметрия.

## Среда

- шина: два адаптера **PEAK System PCAN-USB** (драйвер `pcan_usb`) на одной
  витой паре, терминаторы 120 Ом на обоих концах, `can0` (обслуживается) и
  `can1` (наблюдатель/нагрузка);
- ПО: **пакеты из APT-репозитория проекта** (`/usr/bin`) и пакетный
  `cantcpd.service`;
- проверки: `scripts/hw-smoke.sh --bin /usr/bin`, ручные обмены и
  `scripts/vcan-smoke.sh` для TLS/SIGHUP.

## Путь пакета и сервиса (сценарий пользователя)

| Проверка | Результат |
|---|---|
| `apt install cantcpd cantcp-cli` из репозитория | установлено (первая попытка вскрыла отсутствие `AF_NETLINK` в пакетном юните — исправлено в релизе, см. находки) |
| `systemctl enable --now cantcpd` с пакетным конфигом | сервис активен |
| Обмен через сервис: classic 8 байт, расширенный, 1 байт | эхо клиенту 3/3, `candump` на `can1` 3/3, `frames_read=3`, `frames_written=3`, ошибок нет |
| `systemctl reload cantcpd` (SIGHUP) на живом сервисе | остаётся активным, обмен продолжается |

## Проверки на битрейтах

`scripts/hw-smoke.sh --bin /usr/bin --a can0 --b can1 --bitrate <rate>`:
матрица — 13 классических кадров (8/0/1 байт, remote, расширенный, длины
данных 1..8) плюс нагрузка 1000 кадров от адаптера-наблюдателя.

| Битрейт | Матрица | Нагрузка |
|---|---|---|
| 125 кбит/с | 13/13 кадров дошли до клиента и наблюдателя | 1000/1000 |
| 250 кбит/с | 13/13 | 1000/1000 |
| 500 кбит/с | 13/13 | 1000/1000 |
| 1000 кбит/с | 13/13 | 1000/1000 |

## Находки прогона (все исправлены)

1. **Пакетный юнит блокировал netlink**: в `RestrictAddressFamilies` не было
   `AF_NETLINK`, нужного `net.InterfaceByName`; сервис падал на старте, а
   тот же бинарь, запущенный руками, работал. Исправлено в юните и
   документации, релиз пересобран.
2. **Смоук-скрипты убивали чужие процессы**: `pkill -x cantcpd` в cleanup
   убивал демон пользователя и параллельный soak. Теперь убиваются только
   свои PID.
3. **Фиксированные порты и подсчёт строк**: `vcan-smoke` конфликтовал с
   работающим сервисом и считал чужой трафик; добавлены
   `--listen/--stats`, а матрица сверяет ожидаемые кадры.
4. **`hw-smoke` отправлял CAN FD кадры классическим адаптерам**: матрица
   формировала FD-кадры, которые `can0` (MTU 16) отвергает с `EINVAL`.
   Теперь по умолчанию только классика, `--fd` — для FD-адаптеров.

## Error frames (последний шаг стенда)

Экземпляр с `--error-frames` (и клиент-слушатель) работал с `can0`, пока по
шине шёл трафик (`cangen` на `can1` плюс кадры клиента через демон). Две
попытки вызвать ошибки — снять один терминатор на 2–3 с, затем разорвать
один провод витой пары на 2–3 с — **не дали ни одного error-кадра**:
контроллеры остались `ERROR-ACTIVE` с нулевыми счётчиками ошибок, все кадры
дошли (3656/3656 прочитано в одном из прогонов). На коротком хорошо
терминированном стенде неисправность не доживала до состояния ошибки (или
фактически не вносилась); bus-off исключён решением владельца.

Что покрыто вместо этого:

- `socketcan.Open` выставляет `CAN_RAW_ERR_FILTER` с `CAN_ERR_MASK` при
  `--error-frames` — вызов покрыт юнит-тестом (`TestOpen_ErrorFrames`),
  демон с опцией стартует корректно;
- error-кадры переносятся протоколом как обычные классические и
  отображаются CLI (`#E…` в candump-форме, `"error":true` в JSON);
- loopback и потоковый путь проверены на `vcan` (где TX-кадры ошибок не
  доставляются, как задокументировано).

Среда, которая реально генерирует ошибки (длинная шина, неисправный узел,
несовпадение битрейтов), воспроизведёт путь быстро; результат стенда
зафиксирован как «не воспроизведено».

## Замечания

- Data phase FD остаётся на виртуальной шине: PCAN-USB — классический
  адаптер (без `dbitrate`/`fd on`).

## Вывод

Установленные пакеты работают сквозным образом на реальной шине на 125k,
250k, 500k и 1000 кбит/с: матрица кадров и длительная нагрузка проходят без
потерь, сервис стартует, перечитывается и обслуживает кадры, amd64-клиент
общается с тем же демоном по сети. Опция error frames реализована и покрыта
юнит-тестом; вызвать реальные ошибки на этом стенде не удалось, результат
зафиксирован как «не воспроизведено».
