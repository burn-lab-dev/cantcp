# Тестирование

[English](TESTING.md) | **Русский**

Разрабатывается **[BURN-LAB](https://burn-lab.ru)** — встраиваемый Linux:
драйверы, CAN и промышленная телеметрия.

Две среды, одна матрица:

- **виртуальная шина (vcan)** — работает везде, включая CI, без железа;
- **физическая шина** — два CAN-адаптера на одной витой паре, запускается
  вручную.

## Юнит-тесты

```sh
make test    # go test -race ./...
make fmt vet
make cross   # релизные цели должны собираться
make deb VERSION=v0.0.0
```

Тесты socketcan и e2e сами пропускаются при отсутствии виртуального
интерфейса, поэтому `make test` остаётся зелёным на машине без root.

## Виртуальная шина

```sh
sudo modprobe vcan
sudo ip link add dev vcan0 type vcan
sudo ip link set vcan0 mtu 72      # CAN FD; без MTU 72 запись FD падает
sudo ip link set up vcan0

scripts/vcan-smoke.sh              # полный смоук, ~15 с
scripts/vcan-smoke.sh --report /tmp/cantcp-report
```

Смоук-скрипт собирает бинари, поднимает демон на loopback-портах и
проверяет:

| Проверка | Что доказывает |
|---|---|
| `matrix` | classic/FD/EFF/RTR, все длины данных CAN FD (0..64), эхо клиенту и наблюдение через `candump` |
| `python-interop` | клиент из `cantcp-lib-python` (examples/client.py) обменивается кадрами с Go-`cantcp-cli` через один демон |
| `rate-limit` | 100 кадров в одном соединении при лимите 10 fps: лишние отброшены и посчитаны |
| `idle-timeout` | молчащий клиент отключается |
| `max-connections` | соединение сверх лимита закрывается |
| `tls-mtls` | mutual-TLS-обмен доставляет кадры |
| `tls-version` | TLS 1.2 отвергается |
| `sighup` | сертификат ротируется без рестарта |

Скрипт возвращает ненулевой код при провале и пишет `report.json`,
`report.md` и `report.html` при `--report`.

Дополнительные ручные проверки:

```sh
# Двусторонняя нагрузка и целостность (5000 нумерованных кадров, умеренный темп)
scripts/vcan-smoke.sh --keep && ls /tmp   # артефакты прогона

# Burst-проверка: vcan сам может терять кадры при экстремальном burst (g=0);
# независимый candump теряет так же — это свойство шины, не баг шлюза.
# Умеренные скорости (то, что делает реальная шина CAN) обязаны быть без потерь.
cangen vcan0 -g 1 -I 321 -n 5000
```

## Физическая шина

Соедините два адаптера в одну шину с терминаторами 120 Ом и поднимите их:

```sh
sudo ip link set can0 up type can bitrate 500000
sudo ip link set can1 up type can bitrate 500000
scripts/hw-smoke.sh --a can0 --b can1 --bitrate 500000 --report /tmp/hw-report
```

`--a` обслуживает `cantcpd`, `--b` — наблюдатель и источник нагрузки. Скрипт
повторяет матрицу и умеренную нагрузку на реальной шине; по умолчанию только
классические кадры (`--fd` добавляет FD-набор и требует адаптеров с MTU 72).
Флаг `--bin /usr/bin` тестирует установленные пакеты вместо `bin/`, а
`--listen`/`--stats` позволяют не конфликтовать с работающим сервисом.
Повторите на 125k, 250k, 500k и 1M; для адаптеров с CAN FD — ещё и с data
phase (500k/1M/2M/4M).

Результаты железных прогонов коммитятся в
[docs/test-reports](docs/test-reports/) и зеркалятся на GitHub Pages.

## Что нельзя проверить виртуально

- TX-кадры ошибок: `vcan` их не доставляет (найдено на первом смоуке);
  обработка error frames — проверка на железе;
- bus-off и счётчики ошибок: нужен реальный контроллер (снять терминатор
  или замкнуть пару на стенде);
- реальные битрейты и тайминги FD.

## CI

- `test` — gofmt, vet, `go test -race` на Go 1.24/1.25/1.26;
- `e2e` — поднимает vcan, создаёт `vcan0` с MTU 72, прогоняет
  `go test -race ./...` и `scripts/vcan-smoke.sh`, выкладывает отчёт
  артефактом и в summary джобы;
- `canon` — векторы кодека должны совпадать с `cantcp-spec`;
- `cross` — релизные сборки и `.deb`-пакеты;
- `vuln`, CodeQL, fuzz по расписанию.

## Как добавить проверку

Добавьте сценарий в `scripts/vcan-smoke.sh` блоком
`record PASS|FAIL`, держите его детерминированным (ограниченные таймауты,
без абсолютных таймингов); если нужен hardware — в `scripts/hw-smoke.sh` и
этот документ.
